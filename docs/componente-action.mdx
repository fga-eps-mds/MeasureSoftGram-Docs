# Action

A **Action** é uma **GitHub Action** que roda no seu pipeline de CI, coleta as
métricas do código (do SonarCloud/SonarQube e do GitHub) e as envia ao
[Service](./componente-service.mdx), onde ficam disponíveis para visualização no
[Front](./componente-front.mdx). Veja o fluxo em [Arquitetura](./arquitetura.mdx).

## Como usar no seu workflow

Adicione o passo ao seu workflow de CI, depois da análise do Sonar:

```yaml
- name: Action MeasureSoftGram
  id: msgram
  uses: fga-eps-mds/MeasureSoftGram-Action@v2.1.5
  with:
    githubToken: ${{ secrets.GITHUB_TOKEN }}
    sonarProjectKey: "nome-da-org_nome-do-repositorio"
    msgramServiceToken: ${{ secrets.MSGRAM_SERVICE_TOKEN }}
    productName: "nome-do-seu-produto"
    workflowName: "nome-do-seu-workflow-de-build"
    collectSonarqubeMetrics: true
    collectGithubMetrics: true
    usLabel: "US"
```

Entradas **obrigatórias**: `githubToken`, `productName`, `msgramServiceToken`,
`collectSonarqubeMetrics`, `collectGithubMetrics`. Entradas opcionais: `host`,
`sonartoken`, `sonarProjectKey`, `workflowName`, `usLabel`.

:::tip[Coleta de métricas do GitHub]
Se você ativa `collectGithubMetrics` para medir o tempo de feedback do CI, dispare
a Action num workflow separado, acionado por `workflow_run` após o build concluir.
Assim ela enxerga a execução já finalizada e coleta a métrica corretamente.
:::

## Desenvolvimento local

```bash
git clone https://github.com/fga-eps-mds/MeasureSoftGram-Action.git
cd MeasureSoftGram-Action
yarn install
```

A Action é escrita em TypeScript e compilada com `@vercel/ncc` para `dist/`. Para variáveis
de ambiente locais, copie o template `env-vars-example/.action.env` (chaves:
`GITHUB_TOKEN`, `SONAR_TOKEN`, `MSGRAM_TOKEN`, `MSGRAM_SERVICE_HOST`).

## Como testar

```bash
yarn run jest --coverage --ci --silent
yarn lint
yarn run build
```

## Release e Deploy de Produção

A entrega da Action segue o modelo de versionamento semântico (`vMAJOR.MINOR.PATCH`) com pipeline automatizado no GitHub Actions:

### 1. Gatilhos na branch de produção (`main`)
- **Tags Semânticas (`v*.*.*` ou `v*`):** Qualquer tag criada a partir da branch `main` dispara o workflow `.github/workflows/release.yml`.
- **Releases no GitHub:** Criar ou publicar uma nova release na interface do GitHub também aciona a esteira de build e publicação.

### 2. Etapas da Esteira Automatizada
1. **Validação Rigorosa:** Execução completa de linter (`yarn lint`) e testes unitários com cobertura (`jest`).
2. **Compilação do Bundle (`dist/`):** O código TypeScript em `src/` é compilado via `ncc` para `dist/index.js`, garantindo que o bundle versionado esteja 100% íntegro e sincronizado.
3. **Major Tag Flutuante (`v1`, `v2`):** O workflow identifica a versão major (ex: `v2` a partir de `v2.2.0`) e atualiza automaticamente a tag móvel para o commit recém-compilado. Dessa forma, repositórios clientes que declaram `uses: fga-eps-mds/MeasureSoftGram-Action@v2` recebem melhorias e correções sem quebra de contrato.
4. **Publicação de Release Notes:** Geração automática das notas de versão e upload dos arquivos de execução como assets da release via `softprops/action-gh-release`.

### 3. Como testar com segurança (Dry-Run)
Para validar o pipeline sem afetar tags públicas ou releases de produção:
1. Acesse a aba **Actions** no repositório.
2. Selecione o workflow **Release & Dist Bundle**.
3. Clique em **Run workflow**, selecione a branch de trabalho e marque a opção `dry_run: true`.
4. Todos os passos de validação, testes e compilação serão executados, pulando a movimentação de tags e criação da release pública.
